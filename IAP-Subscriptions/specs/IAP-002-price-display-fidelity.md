# IAP-002 — Price display fidelity

- **Status:** Proposed
- **Group:** IAP & Subscriptions
- **Applies to:** Every app that shows a store price anywhere outside the store's
  own purchase UI — pricing page, marketing site, in-app paywall copy, lifecycle
  email, store listing description.
- **Last updated:** 2026-08-26

## Feature

Every price a user reads **MUST** be the price the store will charge them. Prices
displayed outside the store's own UI **MUST** be generated from the store's price
data and **MUST NOT** be maintained by hand.

## Why "we know our own prices" is false

A store price is not one number. It is a schedule: one entry per territory, per
product, each with a start date, in the store's own rounded and tax-adjusted
tiers. Nobody re-types 175 territories, so what actually gets typed is a
plausible table that then stops tracking reality.

```
  App Store Connect                          the pricing page
  ─────────────────                          ────────────────
  pro.monthly   175 territory prices  ──?──►  monthly:  4.99
  pro.annual    175 territory prices  ──?──►  annual:  29.99
  pro.lifetime  175 territory prices  ──✗──►  lifetime: 79.99   ← charged 39.99
                    ▲                              ▲
        the price the user pays          the price the user was promised

  Drift is silent, one-directional, and survives review: two of the three rows
  being right is what makes the third one invisible.
```

This is the observed failure, not a hypothetical: a hand-kept table advertised a
lifetime unlock at roughly **double** the real store price in **all 43**
currencies it listed, while the monthly and annual rows in the very same table
were correct to the cent. It shipped, and stayed shipped, because the file looked
maintained and nothing compared it to the store.

## Requirement

1. **One generated source.** Every price rendered outside the store UI **MUST**
   originate from a file generated by pulling the provider's API (App Store
   Connect price schedules, Play pricing). The file **MUST** carry a
   *do-not-edit-by-hand* marker and the date it was pulled. Price literals
   **MUST NOT** appear in page templates, plan catalogues or copy.
2. **Every purchasable product, not just the subscriptions.** The generator
   **MUST** cover one-time and non-consumable products as well. These read from a
   *different endpoint* than subscriptions and are the ones routinely forgotten —
   which is precisely where the drift above lived.
3. **Both halves of a non-consumable schedule.** Where a provider splits the
   schedule into a hand-set base and its own equalized territories (ASC
   `manualPrices` vs `automaticPrices`), the generator **MUST** read both, with
   the manual entry winning. Reading only the manual half silently yields a
   single territory; reading only the automatic half silently ignores a
   deliberate price.
4. **Today's price, never a scheduled one.** Schedules contain future price
   changes. An entry whose start date is after today **MUST NOT** be treated as
   the current price.
5. **Currency is the display unit, and collisions resolve by a stated rule.**
   Several territories share a currency, sometimes *at different tiers* (USD and
   EUR both are). The generator **MUST** apply a documented, deterministic rule —
   e.g. the tier the most territories are on — and **MUST NOT** take whichever
   row arrived first.
6. **No arithmetic in place of a published price.** Derived figures (the
   monthly-equivalent of an annual plan, "save N%") **MUST** be computed from
   pulled numbers. A price the store publishes directly **MUST NOT** be
   reconstructed by dividing, converting or FX-rating another one — store tiers
   are per-territory rounded and will not match.
7. **Native surfaces quote the live localized price.** In-app paywalls **MUST**
   render the store SDK's localized price string (StoreKit `displayPrice`,
   RevenueCat package price). The generated table is for surfaces with no store
   SDK — web pages, emails — only.
8. **Regeneration is one command, and idempotent.** A single documented command
   **MUST** regenerate the file, and re-running it against an unchanged store
   **MUST** produce a byte-identical file, so a rerun is itself the drift check.
9. **A price change in the console is not done until it is pulled.** Changing a
   price **MUST** be followed by a regeneration and redeploy; the pull date in
   the generated file is what makes staleness visible in review.
10. **The claim is verifiable before release.** A check that compares the shipped
    table against the provider **MUST** exist and **MUST** run wherever store
    credentials are available — at minimum on the release checklist, in CI where
    credentials allow. "We regenerated it recently" is not a check.

## Rationale

An advertised price that differs from the charged price is a misrepresentation
before it is a bug. It is chargeable under consumer-protection rules in most
markets the app is sold in, it contradicts store metadata accuracy requirements
(App Review 2.3), and when the advertised number is the *higher* one it silently
suppresses conversions no analytics dashboard will ever attribute to it.

The reason to fix it structurally rather than carefully is that careful does not
survive: a price table is edited once at launch and then never again, while the
store console keeps being edited — a promotion here, an equalization there. Any
process that depends on a human remembering to mirror one into the other fails
in the direction of the store being right and the page being wrong, which is the
expensive direction. Generating the file inverts that: the page cannot drift
because there is nothing to drift *from*.

The same logic already governs entitlements in this bundle — success is declared
off the entitlement, never off the call returning
([IAP-001](IAP-001-purchase-progress-feedback.md) §4). This is that rule applied
one step earlier: the price is quoted off the store, never off a local copy.

## Acceptance criteria

- [ ] No price literal appears in any page template, plan catalogue or marketing copy; every one resolves to the generated file.
- [ ] The generated file names its generator, its pull date, and states that it must not be hand-edited.
- [ ] The generated file contains every purchasable product, including non-consumable/one-time unlocks.
- [ ] For a non-consumable, the table's base-territory price equals the hand-set console price, and other territories equal the provider's equalized prices.
- [ ] A price scheduled to start in the future does not appear in the table.
- [ ] A currency served at two tiers resolves to the documented tier, reproducibly.
- [ ] Re-running the generator with no store change produces a byte-identical file (`git diff` empty).
- [ ] Every displayed price matches the store's own checkout sheet for that territory, spot-checked in at least three currencies including one zero-decimal (JPY) and one with a non-USD base.
- [ ] The in-app paywall's price comes from the store SDK, not from the generated table.
- [ ] Changing a price in the store console and redeploying without regenerating is caught by the pre-release check.

## Implementation notes

- **App Store Connect endpoints** (v1, ES256 JWT signed `ieee-p1363` — the DER
  default is rejected with an unexplained 401):
  - subscriptions — `GET /v1/subscriptions/{id}/prices?include=subscriptionPricePoint,territory&limit=200`
  - non-consumables — `GET /v1/inAppPurchasePriceSchedules/{id}/automaticPrices…`
    **and** `…/manualPrices?include=inAppPurchasePricePoint,territory&limit=200`
    (`/v2/inAppPurchases/{id}/iapPriceSchedule/manualPrices` is not a valid path —
    go through the schedule resource, whose id is the IAP id)
  - the price sits on the *included* price point (`customerPrice`), not on the
    price row; the currency sits on the *included* territory.
- **Paginate and pace.** 175 territories × 3 products is several pages; follow
  `links.next`, ~250 ms between calls, exponential backoff on 429.
- **Worked example:** `timelogger/sst/scripts/asc-pull-prices.mjs` →
  `sst/src/prices.generated.ts`, with the page's USD figures derived from that
  file rather than restated (`const USD = PRO_PRICES.USD`).
- **Zero-decimal currencies** (JPY, KRW, CLP…) must survive the round trip as
  integers — formatting with `Intl.NumberFormat(…, {style:'currency'})` handles
  the display, but a generator that forces two decimals corrupts the value.
- Setting the prices up in the first place is
  [`../app-store-iap-setup/`](../app-store-iap-setup/README.md); this spec governs
  what happens to them afterwards.
