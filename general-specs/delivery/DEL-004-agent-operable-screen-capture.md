# DEL-004 — Agent-operable screen capture for release assets

- **Status:** Proposed
- **Group:** Delivery
- **Applies to:** Any product whose release requires screenshots of a running
  desktop UI — App Store listings, landing pages, documentation, review evidence.
- **Cross-cutting:** Feeds [UI-005](../design/UI-005-landing-page-screenshots.md)
  (landing page must showcase product screenshots) and
  [DEL-001](DEL-001-infrastructure-as-code.md) (everything reproducible from the
  repo). Privacy of captured content is a [PRIV-001](../privacy/PRIV-001-data-minimization-and-retention.md)
  concern.
- **Last updated:** 2026-09-06

## Requirement

1. Screenshots that ship — store listings, marketing pages, docs — **MUST** be
   produced by a scripted capture that can be re-run unattended and committed
   alongside the code that produced them. A screenshot taken by hand is not
   reproducible and **MUST NOT** be the source of a shipped asset.
2. The capture path **MUST** be a dedicated, code-signed capture application with
   its own bundle identity, invoked through LaunchServices (`open -a`), so that
   macOS attributes the Screen Recording grant to *that* application.
   Capture **MUST NOT** depend on the grant being held by a terminal emulator:
   TCC attributes a process spawned from a shell to the shell's application, so
   such a grant is tied to whichever terminal happened to run it, is lost when the
   agent runs from another host process, and can only be given by hand.
3. The one-time permission grant **MUST** be a single user action — the system
   prompt raised by the capture app on first use. The tool **MUST** detect the
   absent grant and say exactly what to do, and **MUST NOT** emit a blank, black
   or partial image in its place. A capture that cannot be taken is an error.
4. In-process self-capture — `NSView.cacheDisplay`, `WKWebView.takeSnapshot`,
   `ImageRenderer` — **MAY** be used for content a process owns outright, and is
   the right tool for offscreen rendering with no permission at all. It **MUST
   NOT** be relied on for full-window screenshots of a Cocoa app: views backed by
   vibrancy or materials (`NSVisualEffectView` — sidebars, toolbars, titlebars)
   are composited by the window server and come out **blank**, while ordinary
   layers and WebKit content come out correctly. The result is a plausible image
   that is wrong, which is worse than a failure.
5. Captures **MUST** be produced at the exact pixel dimensions the destination
   requires and **MUST NOT** be resampled afterwards. Where a store rejects an
   image whose size is off by a pixel without saying so, the pipeline **MUST**
   assert the size at capture time.
6. A capture run **MUST** be driven against a committed fixture — a sample
   library, seeded account or demo data — never a real user's content, and any
   personal state the app would restore **MUST** be moved aside for the run and
   restored afterwards, including when the run fails.

## Rationale

Screenshots are the one release asset that cannot be written down, so they are
the one that silently goes stale: a listing keeps showing a UI that shipped three
versions ago because retaking them means a person, a machine and an afternoon.
Making the capture a script makes it a build step.

The permission is what decides the design. Screen capture on macOS is gated by
TCC, and the gate is attached to the *responsible* application rather than to the
process that calls the API — so a helper run from a shell inherits the terminal's
grant, or its absence. Granting a terminal is both too broad (every tool it ever
runs gains the screen) and too fragile (it must be quit and reopened, and another
terminal has none of it). A dedicated capture app with its own identity is
narrower, survives, and is visible in System Settings as one auditable row.

Clause 4 is recorded because the failure is quiet and the temptation is real: an
app can photograph itself with no permission whatsoever, it works for most of the
window, and the parts it misses are exactly the parts that make a Mac screenshot
look like one.

## Acceptance criteria

- [ ] Store and marketing screenshots are regenerated by a documented command that
      needs no interactive step beyond the initial permission grant.
- [ ] The capture tool is a signed `.app` with its own bundle identifier, listed
      under System Settings ▸ Privacy & Security ▸ Screen Recording.
- [ ] Invoking the tool without the grant exits non-zero with a message naming
      the setting, and writes no image.
- [ ] Output dimensions are asserted against the destination's required size, and
      a mismatch fails the run.
- [ ] The capture run uses fixture content only; a reviewer can confirm no
      personal file names, paths or contents appear in any shipped screenshot.
- [ ] Re-running the capture on an unchanged build produces images equivalent to
      the committed ones.

## Implementation notes

- **markdown-preview (Markdown Dark Reader):** `marketing/appstore/` holds the
  capture, the caption template and the renderer; `Scripts/upload-screenshots.py`
  puts the result on the listing. The macOS store canvas is `2880 × 1800`, which a
  1440 × 900 point window produces exactly at 2× backing scale — asserted after
  every shot rather than assumed.
- Self-capture was tried there first and is the origin of clause 4: the reader
  pane (a `WKWebView`) rendered perfectly through `cacheDisplay`, while the
  SwiftUI sidebar and the unified toolbar rendered as white rectangles.
- Prefer `ScreenCaptureKit` (`SCScreenshotManager`) on macOS 14+ over the
  deprecated `CGWindowListCreateImage`; both sit behind the same TCC gate, so the
  choice is about API longevity, not permissions.
- `tccutil` can only *reset* a grant, never give one — there is no scripted path
  to permission, which is why clause 3 asks for the prompt rather than a document
  telling somebody to go and find System Settings.
